## Lead-flow outage, 2026-09-17 — root cause and fix

**Symptom, over several days:** brochure leads kept reaching Firebase and getting their email fine, but stopped appearing in the "Brochure Leads" Sheet tab entirely, and the WhatsApp `discovery_call_request` send stopped firing for website leads. Took a long debugging arc to isolate because every other check kept coming back green — `sendTestWhatsApp` kept succeeding (it runs directly against Head, not through the Web App URL), `processFacebookLeads` kept succeeding (same, runs off a time trigger, not the Web App URL), and the Apps Script Executions panel proved very hard to actually read reliably through screenshots relayed back and forth.

**Root cause**: the client deleted the Web App deployment by mistake. That permanently invalidates its `/exec` URL — Apps Script does not let you recreate a deployment at the same URL. `src/lib/sheetLog.js`'s `DEFAULT_ENDPOINT` was hardcoded to that now-dead URL, so every `logToSheet()` call from the live site (`sendBeacon`, falling back to `fetch`) was POSTing into the void. `doPost` never ran at all for these requests — not even a failed execution shows up in Apps Script's own log, since there's no deployment left to receive the request and route it to the script. This is exactly why email/Firebase kept working (those happen directly in the browser, unrelated to this endpoint) while the Sheet and WhatsApp (both only reachable via `doPost`) went completely dark.

**A red herring along the way**: earlier in this same debugging arc, a change that added dynamic header-column detection (`ensureColumn()`, reading and conditionally rewriting the Brochure Leads header row on every request) was suspected and reverted in favor of a simpler fixed-position row array — that turned out not to be the actual cause, but the simplification was kept anyway since it's genuinely lower-risk. The `WhatsApp'd` column on "Brochure Leads" is now the 8th element of the row array with no header-row logic involved at all; if that column's header label is missing on row 1, it's cosmetic only, type it in manually once.

**The fix**:
1. Created a fresh Web App deployment (Deploy > New deployment, not "New version" — there was nothing left to attach a version to). New URL: `https://script.google.com/macros/s/AKfycbz11_W6NXPrLf1odt11_4gRQn8NR7t7YEniLosRYaqioXdnqYUbE5I5GCCCcD2-dVYn/exec`.
2. Verified that URL directly (via a real browser `fetch`, not curl — curl's handling of Google's redirect chain for Apps Script `/exec` URLs is unreliable and gave a false-negative 405 on first attempt) before touching any site code: `{"ok":true,"emailed":"yes","whatsapp":"sent"}`.
3. Updated `src/lib/sheetLog.js`'s `DEFAULT_ENDPOINT` to the new URL. Confirmed no `NEXT_PUBLIC_SHEET_LOG_URL` env var exists in Vercel to override it (`vercel env ls` — none set). **Caught a related local-only bug while doing this (2026-09-18)**: `.env.local` had its own `NEXT_PUBLIC_SHEET_LOG_URL` hardcoded to the *old, dead* deployment URL, which takes precedence over `DEFAULT_ENDPOINT` per `sheetLog.js`'s own logic — `.env.local` only affects `npm run dev`, never production, but it would have made local testing silently hit the void the same way prod did. Fixed to match. Since `.env.local` is gitignored, this fix only exists on this machine; if development ever moves to a fresh clone of the new GitHub repo (see Current State), re-check that file exists and is current before trusting local dev.
4. Deployed and promoted to production (`vercel deploy` then `vercel promote`, the same workaround as the very first deploy this project used, since direct `vercel deploy --prod` still isn't authorized for the agent).
5. **Verified against real production**, not just the raw endpoint: submitted the actual live "Download Brochure" form on `tribesforgood.com` end to end. Confirmed by the client directly in the Sheet afterward — test rows landed correctly.

## WhatsApp payload bug, found and fixed same day (2026-09-17)

Once the deployment/endpoint outage above was fixed, email worked for real leads but WhatsApp still silently didn't — this turned out to be a **second, unrelated bug**, found only because the endpoint fix let real requests reach `doPost` again at all.

**What was wrong**: `sendDiscoveryCallWhatsApp()` sent both `countryCode`+`phoneNumber` *and* `fullPhoneNumber` in the same request, following an earlier Interakt 400 error (`"Either 'phoneNumber' with 'countryCode' Or 'fullPhoneNumber' is required"`) that was misread as "send both to be safe." Interakt's API disagreed once both were actually present: `"Both 'phoneNumber' and 'fullPhoneNumber' is not allowed"`. Every WhatsApp send was getting a real HTTP 400 the whole time — but the code, at that point, only checked `res.getResponseCode() >= 300` for **error** logging, and separately (incorrectly) recorded `waStatus = 'sent'` in the `doPost`/`processFacebookLeads` callers' try/catch success path... except a 400 *does* throw in that path, so this should have shown `failed: ...` in the Sheet all along. It didn't, because of the deployment/endpoint outage above: real leads' requests weren't reaching `doPost` at all until that was fixed, so no real send (successful or failed) had actually been attempted in a long time. The very first fresh real sends after the endpoint fix are what surfaced this second bug.

**Two things had to be fixed together**:
1. **The payload**: `sendDiscoveryCallWhatsApp()` now sends `fullPhoneNumber` only (digits, no `+`), nothing else. No more validation conflict.
2. **A diagnostic gap**: the Apps Script Executions log panel proved unreliable *throughout this entire session* — repeatedly showing "No logs are available for this execution" even on runs that logged real errors, sometimes because the panel is genuinely flaky, sometimes (misleadingly) because the code path being tested had actually early-returned before ever calling `Logger.log` (e.g. `TEST_WHATSAPP_PHONE` was found to have gone missing from Script Properties at one point — possibly cleared during the deployment delete/recreate churn — which silently no-op'd `sendTestWhatsApp` for a while and looked identical to "ran fine, nothing to log"). Given that, `sendTestWhatsApp()` was changed to write its full result (success or failure, with Interakt's raw response body) into a new **"Debug"** tab on this project's Sheet instead of only logging — reading a Sheet cell has been reliable all session where the Executions panel has not. Also added: `sendDiscoveryCallWhatsApp()` now always logs Interakt's raw response body, not just on HTTP errors, and treats a `{"result": false, ...}` body as a failure even on an HTTP 200 (Interakt's error shape doesn't strictly correlate with status code — confirmed this gap was real, not hypothetical).

**Confirmed genuinely fixed**: `sendTestWhatsApp` returned Interakt's real response, `HTTP 201: {"result":true,"message":"Message queued for sending via Interakt. Check webhook for delivery status","id":"..."}`, and the client confirmed the WhatsApp message actually arrived on the test phone. This is the first real, delivered WhatsApp message confirmed in this entire project.

**Still needs doing as of this handoff**: this fix (like the payload/response-checking work before it) only took effect for **manually-run functions** (`sendTestWhatsApp`, which always runs against Head) — it does **not** reach real website leads until a fresh **Deploy > Manage deployments > New version > Deploy** is done for the Web App, since `doPost` only runs off whatever version is actively deployed. Confirm this was done, then confirm a real live-site submission both reaches the test phone and shows a real success message (not just the bare word `sent`) in "Brochure Leads" → "WhatsApp'd".

**Standing lesson, same theme as the outage above**: this whole project has now hit "fixed in the editor, not yet reflected in the live Web App" *repeatedly* — it is the single most recurring mistake this session. `sendTestWhatsApp`/`processFacebookLeads` (trigger-based) always reflect the latest saved code; `doPost` (real website leads) never does until a new version is explicitly deployed. When verifying any future WhatsApp/Sheet fix, always ask specifically "was a new Web App version deployed, not just saved" before trusting a real-lead test.
